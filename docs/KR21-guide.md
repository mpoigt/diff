# КР № 1. Серверная разработка

Вариант 81. Сервер сравнивает две версии текстового файла и хранит результат в PostgreSQL.

## Что сделано

1. На Express подключены маршруты регистрации, входа и чтения профиля. Регистрация сохраняет хеш bcrypt, а сервер выдаёт JWT и проверяет его на маршрутах записи.
2. Модели Sequelize описывают `User`, `Diff`, `Session` и `AuditLog`. У сравнения есть название, автор, два файла, статистика, история изменений и уникальный `slug`.
3. Реализованы список, детали, создание, полная замена, частичное обновление и удаление. Владельцы могут менять свои записи. Модератор может редактировать любые, удаление доступно администратору.
4. Доступны сортировка, поиск по `slug`, фильтрация и сводка через `GET /api/diffs/stats`.
5. Joi проверяет тело запросов, параметры и UUID. Схемы отклоняют поля, которые заполняются сервером.
6. Контракты описаны в [API.md](../API.md). Тестовые запросы сохранены в [коллекции Postman](DiffServiceAPI.postman_collection.json).

## Запуск

1. Установите Node.js и PostgreSQL. Выполните `npm ci`.
2. Скопируйте `.env.example` в `.env`. Создайте два разных случайных секрета JWT и задайте строку подключения и данные учебного администратора.
3. Выполните `npm run db:create` и затем `npm start`. Маршрут `GET /health` должен вернуть статус 200.
4. Для полного тестового прогона откройте отдельную тестовую БД. Перед стартом сервера задайте `AUTH_RATE_LIMIT_MAX=200`, `RATE_LIMIT_MAX=5000` и `USER_RATE_LIMIT_MAX=500`.
5. Запустите `npm run smoke`. При нестандартном порте укажите `SMOKE_BASE_URL`, а при других учётных данных администратора передайте `ADMIN_EMAIL` и `ADMIN_PASSWORD` через окружение тестового процесса. Повышенные лимиты предназначены для тестовой среды.

## Порядок проверки

1. Зарегистрируйте пользователя и войдите. Проверьте `GET /auth/me` с JWT и без него.
2. Создайте сравнение и получите его по UUID и `slug`. Проверьте, что одинаковые заголовки приводят к разным `slug`.
3. Измените запись от имени владельца и получите статистику. Попытка удалить запись от имени пользователя даёт 403, администратор получает 204.
4. Выполните запрос с некорректным адресом почты, слабым паролем или полем вне схемы. Ожидаемый статус — 400.
