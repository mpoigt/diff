# Отчёт по лабораторной работе

**Тема курсового проекта:** Сервис для сравнения файлов (diff-инструмент) с визуализацией изменений.
**Тема работы:** Создание серверного приложения на Node.js (Express.js).

## 1. Цель работы

Приобрести практические навыки создания серверного приложения на платформе Node.js с
использованием фреймворка Express.js: изучить маршрутизацию, обработку HTTP-запросов
разных типов (GET, POST, PUT, PATCH, DELETE), формирование ответов сервера и обработку
ошибок для последующей интеграции с клиентской частью курсового проекта.

## 2. Краткое описание проекта

Предметная область — сервис сравнения текстовых файлов. Пользователь передаёт на сервер
две версии файла, сервер строит построчный diff и сохраняет результат в истории сравнений.
Ресурс называется `diffs`; каждая запись содержит название сравнения, автора, оба файла,
статистику изменений и список операций (`equal` / `added` / `removed`), пригодный для
отрисовки на клиенте.

Diff рассчитывается на сервере алгоритмом на основе LCS (наибольшей общей
подпоследовательности): строится матрица длин LCS, затем восстанавливается путь, из
которого получается последовательность операций с номерами строк в старом и новом файле.
Дополнительно считается статистика: количество добавленных/удалённых/неизменённых строк
и процент схожести файлов.

Хранилище — массив в памяти сервера (по условию работы). Логика разделена по слоям
`routes → controllers → models`, поэтому в следующих работах массив можно заменить на
базу данных, не меняя маршруты и контроллеры.

### src/controllers/diffs.controller.js (фрагменты)

```js
// POST /api/diffs
function create(req, res, next) {
  const errors = validateCreate(req.body);
  if (errors.length > 0) {
    return next(ApiError.badRequest('Некорректные данные запроса', errors));
  }
  const diff = Diff.create(req.body);
  res.location(`/api/diffs/${diff.id}`);
  return res.status(201).json(diff);
}

// GET /api/diffs/:id
function getOne(req, res, next) {
  const diff = Diff.findById(req.params.id);
  if (!diff) {
    return next(ApiError.notFound(`Сравнение с id=${req.params.id} не найдено`));
  }
  return res.status(200).json(diff);
}

// DELETE /api/diffs/:id
function remove(req, res, next) {
  const deleted = Diff.remove(req.params.id);
  if (!deleted) {
    return next(ApiError.notFound(`Сравнение с id=${req.params.id} не найдено`));
  }
  return res.status(204).end();
}
```

### src/middleware/errorHandler.js (глобальная обработка ошибок)

```js
function errorHandler(err, req, res, next) {
  if (err.type === 'entity.parse.failed') {
    return res.status(400).json({ error: 'Тело запроса не является корректным JSON' });
  }

  const status = err.status || 500;
  if (status >= 500) console.error('[error]', err.stack || err.message);

  const body = { error: status >= 500 ? 'Внутренняя ошибка сервера' : err.message };
  if (err.details) body.details = err.details;

  return res.status(status).json(body);
}
```

### src/utils/diffEngine.js (ядро сравнения)

```js
function computeDiff(oldText, newText) {
  const a = splitLines(oldText);
  const b = splitLines(newText);
  const lcs = buildLcsMatrix(a, b);

  const changes = [];
  let i = 0; let j = 0;

  while (i < a.length && j < b.length) {
    if (a[i] === b[j]) {
      changes.push({ type: 'equal', oldLine: i + 1, newLine: j + 1, content: a[i] });
      i += 1; j += 1;
    } else if (lcs[i + 1][j] >= lcs[i][j + 1]) {
      changes.push({ type: 'removed', oldLine: i + 1, newLine: null, content: a[i] });
      i += 1;
    } else {
      changes.push({ type: 'added', oldLine: null, newLine: j + 1, content: b[j] });
      j += 1;
    }
  }
  // ...хвосты обоих файлов и подсчёт статистики
}
```

## 6. Ответы на контрольные вопросы

**1. Какие методы HTTP вы реализовали и для каких операций?**
GET — чтение (список сравнений, одно сравнение, unified-патч, `/health`); POST — создание
новой записи сравнения; PUT — полная замена существующей записи; PATCH — частичное
обновление отдельных полей; DELETE — удаление записи. Дополнительно обрабатывается
OPTIONS — предварительный (preflight) запрос браузера в CORS-middleware.

**2. Как получить параметры из URL (route params) и строку запроса (query string) в Express?**
Route params описываются в шаблоне маршрута через двоеточие и доступны в `req.params`:
для `router.get('/:id', ...)` идентификатор — это `req.params.id`. Параметры строки запроса
Express разбирает автоматически в объект `req.query`: для `GET /api/diffs?search=config&limit=1`
получаем `req.query.search === 'config'` и `req.query.limit === '1'`. Важно, что значения
`req.query` и `req.params` — всегда строки, поэтому числа нужно приводить и валидировать
(в проекте это делает функция `parsePositiveInt`). Данные тела запроса — в `req.body`,
но только после подключения парсера.

**3. Для чего используется middleware express.json()?**
Тело HTTP-запроса приходит потоком байтов, и по умолчанию `req.body` равен `undefined`.
`express.json()` читает поток, проверяет заголовок `Content-Type: application/json`,
разбирает текст через `JSON.parse` и кладёт результат в `req.body`. Дополнительно он
ограничивает размер тела (в проекте `limit: '1mb'`) и при синтаксической ошибке JSON
генерирует ошибку с `err.type === 'entity.parse.failed'`, которую перехватывает глобальный
обработчик и превращает в 400.

**4. Какой HTTP-статус возвращается при успешном создании ресурса? При успешном удалении?**
При создании — **201 Created**, обычно вместе с заголовком `Location`, указывающим URL
нового ресурса (в проекте `Location: /api/diffs/3`), и телом с созданным объектом.
При удалении — **204 No Content**, если тело ответа не возвращается (наш вариант), либо
**200 OK**, если сервер отдаёт удалённый объект или сообщение.

**5. Что такое REST API? Перечислите основные принципы REST.**
REST (Representational State Transfer) — архитектурный стиль построения веб-сервисов,
в котором данные представлены как ресурсы с уникальными URI, а действия над ними
выражаются стандартными методами HTTP. Основные принципы:
- **клиент-серверная архитектура** — разделение ответственности интерфейса и хранения данных;
- **отсутствие состояния (stateless)** — каждый запрос самодостаточен, сервер не хранит
  состояние сессии между запросами;
- **единообразный интерфейс** — ресурсы адресуются URI, а операции выполняются
  стандартными методами (GET/POST/PUT/PATCH/DELETE) с осмысленными кодами статусов;
- **кэшируемость** — ответы явно помечаются как кэшируемые или нет;
- **многослойность** — между клиентом и сервером могут быть прокси и балансировщики;
- **code on demand** (необязательный) — возможность передать клиенту исполняемый код.

**6. Как организовать глобальную обработку ошибок в Express?**
Нужно объявить middleware с **четырьмя** аргументами `(err, req, res, next)` — по их
количеству Express отличает обработчик ошибок от обычного middleware — и подключить его
**последним**, после всех маршрутов. Любая ошибка, переданная через `next(err)`, а также
синхронно выброшенная в обработчике, попадёт именно туда. В проекте это
`src/middleware/errorHandler.js`: он определяет статус (`err.status || 500`), логирует
только серверные ошибки, скрывает их подробности от клиента и отвечает единым JSON.
Перед ним стоит `notFound`, который для несуществующих маршрутов создаёт ошибку 404.
Важно: ошибки из асинхронного кода нужно передавать явно (`try/catch` + `next(err)`),
иначе Express 4 их не поймает.

**7. Какую структуру ответа сервера вы выбрали для ошибок?**
Единый формат: обязательное поле `error` с человекочитаемым сообщением и необязательный
массив `details` со списком конкретных проблем валидации:

```json
{ "error": "Некорректные данные запроса",
  "details": ["Поле \"title\" обязательно и должно быть непустой строкой"] }
```

Такой формат удобен клиенту: `error` можно показать как заголовок ошибки, а `details` —
подсветить у соответствующих полей формы.

**8. Как протестировать DELETE-запрос, если ресурс уже был удалён? Какой статус должен быть возвращён?**
Нужно выполнить DELETE дважды подряд: первый раз ресурс существует — ответ 204,
второй раз записи уже нет — сервер возвращает **404** с телом
`{ "error": "Сравнение с id=3 не найдено" }`. Такое поведение реализовано в проекте
(пункты 13–14 раздела 5). Существует и второй допустимый подход: считать DELETE
идемпотентным и всегда отвечать 204, поскольку конечное состояние («ресурса нет»)
одинаково; вариант с 404 выбран как более информативный для клиента.

**9. Какие преимущества даёт использование nodemon в процессе разработки?**
Nodemon следит за файлами проекта и автоматически перезапускает сервер при их изменении:
не нужно вручную останавливать и запускать `node server.js` после каждой правки. Это
ускоряет цикл «изменил — проверил», сразу показывает ошибки запуска в консоли и позволяет
настраивать отслеживаемые каталоги и расширения. Nodemon ставится как **dev-зависимость**,
так как в продакшене не нужен: там приложение запускается через `npm start` и управляется
менеджером процессов.

**10. В чём разница между методами PUT и PATCH? Какой из них вы реализовали и почему?**
PUT полностью заменяет ресурс: клиент передаёт все обязательные поля, а отсутствующие
затираются. PUT идемпотентен — повторный одинаковый запрос не меняет результат.
PATCH передаёт только изменяемые поля, остальные сохраняются.
Реализованы оба. PUT требуется по условию работы, и для нашего ресурса он логичен: при
замене содержимого файлов diff пересчитывается целиком. PATCH добавлен для практичного
сценария — переименовать сравнение, не пересылая содержимое обоих файлов (пересчёт diff
запускается только если в теле пришли `fileA` или `fileB`).

**11. Как можно добавить поддержку CORS в ваше приложение? (Теоретически)**
Браузер блокирует запросы к другому источнику (origin), если сервер не прислал
соответствующие заголовки. Стандартный способ — пакет `cors`:

```js
const cors = require('cors');
app.use(cors({ origin: 'http://localhost:5173', methods: ['GET','POST','PUT','PATCH','DELETE'] }));
```

Без зависимостей то же делается своим middleware, что и сделано в проекте
(`src/middleware/cors.js`): выставляются заголовки `Access-Control-Allow-Origin`,
`Access-Control-Allow-Methods`, `Access-Control-Allow-Headers`, а на preflight-запрос
`OPTIONS` возвращается 204. Это понадобится при подключении React-фронтенда из 1 части
курса, который работает на другом порту.

**12. Почему в данном задании данные хранятся в массиве, а не в базе данных? Когда стоит переходить на БД?**
Массив позволяет сосредоточиться на теме работы — маршрутизации, HTTP-методах и обработке
ошибок — не тратя время на установку и настройку СУБД. Недостаток очевиден: данные живут
только в памяти процесса и пропадают при перезапуске (в том числе при каждом перезапуске
nodemon), их нельзя разделить между несколькими экземплярами приложения, нет транзакций,
индексов и эффективного поиска. Переходить на БД следует, когда нужны сохранность данных
между перезапусками, объём данных превышает разумный размер памяти, требуется
конкурентный доступ, поиск по индексам или горизонтальное масштабирование — то есть уже
в следующей лабораторной работе. В проекте это упрощено: все обращения к массиву собраны
в `src/models/diff.model.js`, и заменить их на запросы к БД можно, не трогая контроллеры.

**13. Какой заголовок Content-Type должен быть установлен для отправки JSON-данных?**
`Content-Type: application/json` (при необходимости с указанием кодировки —
`application/json; charset=utf-8`). Без него `express.json()` не станет разбирать тело и
`req.body` останется пустым объектом. Тот же заголовок сервер ставит в ответах — метод
`res.json()` делает это автоматически.

**14. Напишите пример curl-команды для тестирования вашего POST-эндпоинта.**

```bash
curl -i -X POST http://localhost:3000/api/diffs \
  -H "Content-Type: application/json" \
  -d '{"title":"test","fileA":{"name":"a.txt","content":"line1\nline2"},"fileB":{"name":"b.txt","content":"line1\nline2 changed\nline3"}}'
```

Ключ `-i` выводит заголовки ответа, чтобы видеть статус `201 Created` и `Location`.
В PowerShell кавычки внутри JSON нужно экранировать (`\"`) или использовать
`Invoke-RestMethod`.

**15. Как убедиться, что сервер работает корректно после каждой модификации кода?**
Смотреть в консоль nodemon: он перезапускает процесс и сразу показывает ошибки
инициализации. Затем прогнать контрольный набор запросов — в проекте для этого есть файл
`requests.http` (REST Client в VS Code) с проверками всех эндпоинтов, включая ошибочные
сценарии 400 и 404, и служебный маршрут `/health`. Каждый запрос логируется middleware
`logger` в формате «метод — путь — статус — время». В дальнейшем эти ручные проверки
стоит заменить автоматическими тестами (Jest + Supertest), чтобы прогонять весь набор
одной командой.

**16. Какие шаги нужно предпринять, чтобы запустить ваше приложение на другом компьютере?**
1. Установить Node.js (версия 18 или новее) и npm.
2. Склонировать репозиторий и переключиться на ветку работы: `git clone <url>`,
   `git checkout lab21`.
3. В корне проекта выполнить `npm install` — зависимости ставятся по `package.json`
   и `package-lock.json` (каталог `node_modules` в репозиторий не коммитится, он в `.gitignore`).
4. Запустить: `npm start` (или `npm run dev` для разработки). При необходимости задать
   другой порт переменной окружения `PORT`.
5. Проверить доступность: открыть `http://localhost:3000/health` и `http://localhost:3000/`.

## 7. Выводы

В ходе работы создано серверное приложение на Node.js с использованием Express.js,
реализующее REST API для предметной области курсового проекта — истории сравнений файлов.
Освоены: подключение и порядок выполнения middleware, маршрутизация с параметрами пути
и строкой запроса, разбор JSON-тела, формирование ответов с корректными HTTP-статусами
(200, 201, 204, 400, 404) и централизованная обработка ошибок через middleware с четырьмя
аргументами.

Помимо обязательных CRUD-операций реализованы фильтрация и пагинация списка, метод PATCH,
выдача патча в unified-формате и собственный алгоритм построчного сравнения на основе LCS,
благодаря чему сервер отдаёт готовые к отрисовке данные, а не просто хранит их. Код
разделён на слои `routes / controllers / models`, что позволит в следующих работах
заменить массив в памяти на базу данных, добавить JWT-аутентификацию и подключить
React-фронтенд из первой части курса, не переписывая существующие маршруты.

Все эндпоинты протестированы; полученные статусы и тела ответов соответствуют ожидаемым.
