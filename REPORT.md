## 1. Цель работы

Создать REST API с системой аутентификации, валидацией данных, защитой от
распространённых уязвимостей (OWASP Top 10) и ролевой моделью доступа для
серверной части курсового проекта.

В рамках работы требовалось:

- разработать структуру проекта (маршруты, контроллеры, модели, middleware);
- реализовать модель пользователя и эндпоинты аутентификации на JWT;
- внедрить ролевую модель минимум из трёх ролей с middleware `roleGuard`;
- обеспечить обязательные меры защиты (helmet, rate limiting, валидация,
  защита от SQL-инъекций через ORM);
- выбрать и обосновать не менее трёх дополнительных мер безопасности;
- реализовать CRUD основной сущности проекта с учётом ролей;
- настроить логирование подозрительных действий;
- подготовить коллекцию Postman и документацию API.

## 2. Краткое описание предметной области

Предметная область — **сервис сравнения текстовых файлов**. Пользователь передаёт
на сервер две версии файла, сервер строит построчный diff алгоритмом на основе
LCS (наибольшей общей подпоследовательности) и сохраняет результат в истории
сравнений. Каждая запись содержит название, автора, оба файла, статистику
изменений и список операций (`equal` / `added` / `removed`), пригодный для
отрисовки на клиенте.

### Почему для этого проекта важна именно безопасность

Сервис работает с **чужим исходным кодом и конфигурационными файлами**. В сравниваемые
файлы пользователи кладут фрагменты реальных проектов, миграции БД, файлы настроек —
то есть данные, которые в открытом доступе оказаться не должны. Из этого следуют
три приоритета, определившие выбор мер защиты:

1. **История сравнений — приватный ресурс.** Чужую запись нельзя ни прочитать по
   перебору идентификатора, ни изменить, ни удалить. Отсюда: UUID вместо
   автоинкремента, проверка владения ресурсом, ролевая модель.
2. **Содержимое файлов — произвольный текст, в том числе HTML, JS и SQL.** Сервис
   обязан принимать `<script>` и `DROP TABLE` как ДАННЫЕ и ни в каком виде их не
   исполнять. Отсюда: ORM с параметризованными запросами, экранирование на выводе, CSP.
3. **Учётная запись = доступ ко всему коду пользователя.** Компрометация пароля
   обходится дороже, чем в обычном CRUD-приложении. Отсюда: политика сложности
   пароля, блокировка после перебора, короткие access-токены, refresh в httpOnly cookie,
   ограничение числа сессий.

### Что изменилось по сравнению с предыдущей версией проекта

| | Было | Стало |
|---|---|---|
| Хранилище | массив в памяти процесса | PostgreSQL + Sequelize, 4 таблицы |
| Идентификаторы | последовательные числа `"1"`, `"2"` | UUID v4 |
| Аутентификация | отсутствовала | JWT access + refresh, bcrypt |
| Права доступа | все операции доступны всем | 3 роли, проверка владения ресурсом |
| Валидация | самописные функции | Joi + встроенные валидаторы Sequelize |
| Поле `author` | принималось от клиента | подставляется из токена |
| Защита | лимит тела 1 МБ, CORS `*` | 8 обязательных + 13 дополнительных мер |
| Логирование | `console.log` метода и статуса | winston, 4 канала с ротацией |

Формат ответов публичных `GET`-эндпоинтов сохранён, поэтому клиентская часть и
прежние запросы продолжают работать.

## 4. Архитектура и структура проекта

### 4.1. Слои

```
HTTP-запрос
    │
    ├─ 1. helmet                 заголовки безопасности, CSP, X-Frame-Options
    ├─ 2. httpLogger             лог запроса и подозрительных статусов
    ├─ 3. CORS white list        отсечение чужих origin
    ├─ 4. globalLimiter          300 запросов / 15 мин с IP
    ├─ 5. requireJsonContentType только application/json
    ├─ 6. express.json({limit})  разбор тела с лимитом 100 КБ
    ├─ 7. cookieParser           refresh-токен из httpOnly cookie
    ├─ 8. sanitizeBody           удаление HTML-тегов из метаданных
    │
    └─ router
        ├─ authenticate()        проверка JWT, загрузка пользователя из БД
        ├─ roleGuard(role)       проверка уровня роли
        ├─ userLimiter           лимит по user ID
        ├─ validate(schema)      Joi: body / params / query
        ├─ ownerOrRole()         проверка владения ресурсом
        ├─ audit(action)         запись в audit log
        └─ controller            бизнес-логика
                │
                └─ model (Sequelize) → PostgreSQL
    │
    ├─ notFound                  404 + отметка сканеров
    └─ errorHandler              generic errors в production
```

Порядок middleware выстроен **от дешёвых проверок к дорогим**: чужой origin, флуд
и неверный Content-Type отсекаются до разбора тела, а тело — до обращения к БД и
вычисления bcrypt-хеша. Поэтому попытка подбора пароля упирается в rate limit
раньше, чем успевает нагрузить процессор.

### 5.2. Решения по схеме и их обоснование

| Решение | Обоснование |
|---|---|
| `id` — UUID v4, а не `SERIAL` | последовательные id позволяют перебрать все записи (`/api/diffs/1`, `/2`, …) и оценить объём данных сервиса. UUID не угадывается |
| `passwordHash` ограничен 72 символами | bcrypt учитывает только первые 72 байта; лишнее место в колонке не нужно |
| Пароль в открытом виде не хранится и не логируется никогда | единственное применение — передать в `bcrypt.hash` / `bcrypt.compare` |
| `role` — ENUM, а не строка | СУБД сама отвергнет значение вне списка; это третий рубеж после Joi и валидатора модели |
| refresh-токены в таблице `sessions`, а не в колонке `users.refreshToken` | пользователь работает с нескольких устройств; одна колонка позволила бы держать лишь одну сессию и не дала бы реализовать меру №20 |
| В `sessions` хранится **SHA-256 хеш** токена | утечка таблицы не даёт возможности войти под пользователем — как и с паролями |
| `stats` и `changes` — JSONB | результат diff — вложенная структура переменной длины; JSONB позволяет фильтровать по полю (`stats.identical`), значения уходят в БД параметром |
| `diffs.ownerId` — `ON DELETE SET NULL` | история сравнений не должна исчезать при удалении пользователя; владелец просто обнуляется |
| `sessions.userId` — `ON DELETE CASCADE` | сессия без пользователя бессмысленна и опасна |
| `audit_logs` без FK-ограничения на `actorId` | запись журнала обязана сохраниться, даже если администратора потом удалили; поэтому email и роль дублируются текстом |
| `audit_logs` без `updatedAt` | журнал аудита неизменяем по определению |

## 6. Обоснование выбранных дополнительных мер безопасности

Задание требует не менее трёх мер. Реализовано **13 из таблицы задания** (плюс
четыре смежные, перечисленные в конце раздела). Ниже — почему выбрана именно
каждая из них применительно к сервису сравнения файлов.

### Мера №3. Проверка сложности пароля

**Требования:** минимум 8 символов, строчная и заглавная латинские буквы, цифра,
специальный символ, без пробелов; пароль не входит в список 20 самых
распространённых.

**Почему для этого проекта.** Учётная запись даёт доступ ко всему загруженному
пользователем коду. Слабый пароль обесценивает все остальные меры: подобрав
`qwerty123`, атакующий получает легальный токен и проходит сквозь ролевую модель
штатно. Проверка на входе дешева, а эффект прямой — убирает самый массовый
вектор атаки.

Реализация: `src/utils/password.js`, функция `checkPasswordStrength` возвращает
**список всех** нарушенных правил сразу, а не первое — иначе пользователь угадывает
требования методом перебора.

### Мера №5. JWT с refresh-токеном в httpOnly cookie

**Как устроено.** Два токена с **разными** секретами:

- access — 15 минут, передаётся в `Authorization: Bearer`, живёт в памяти JS;
- refresh — 7 дней, отдаётся **только** как `HttpOnly; SameSite=Strict` cookie.

**Почему для этого проекта.** Без refresh-токена приходится выбирать между
«токен живёт долго» (украденный токен долго работает) и «пользователь
перелогинивается каждые 15 минут». Разделение снимает выбор: короткий access
ограничивает окно использования украденного токена, а долгоживущий refresh
недоступен JavaScript, поэтому XSS его не уводит. `SameSite=Strict`
дополнительно закрывает CSRF на `/auth/refresh` — cookie не отправится при
запросе с чужого сайта.

**Ротация.** Каждое обращение к `/auth/refresh` отзывает старую сессию и выдаёт
новую пару. Если refresh-токен использовали повторно (подпись верна, а сессии
уже нет) — это признак кражи, и система отзывает **все** сессии пользователя,
записав событие `REFRESH_TOKEN_REUSE`.

Реализация: `src/services/token.service.js`.

### Мера №6. Ограничение попыток входа: 5 неудач → блокировка на 15 минут

**Почему для этого проекта.** Rate limiting по IP (обязательная мера) защищает от
флуда, но не от распределённого перебора: атакующий с пула адресов делает по
нескольку попыток с каждого IP и в лимит не попадает. Блокировка **аккаунта**
работает по другому ключу — по пользователю, — поэтому перебор одного пароля
становится невозможен независимо от числа адресов.

**Детали реализации.** Счётчик `failedAttempts` в таблице `users`; при достижении
лимита выставляется `lockUntil = now + 15 мин`, счётчик обнуляется, и **все
активные сессии отзываются** — если пароль подбирают, он мог уже утечь. Вход с
верным паролем в период блокировки тоже отклоняется (423 Locked). Администратор
может снять блокировку досрочно: `POST /api/users/:id/unlock`.

Реализация: `src/controllers/auth.controller.js`, функция `login`.

### Мера №7. Audit log действий администратора

**Почему для этого проекта.** Администратор может удалить любое сравнение и
понизить роль любому пользователю — то есть безвозвратно уничтожить чужую работу.
Без журнала невозможно ни разобрать инцидент, ни разграничить ответственность между
несколькими администраторами.

**Детали.** Middleware `audit(action)` подписывается на событие `finish` ответа и
пишет запись **после** отправки ответа, поэтому не замедляет запрос. В журнал
попадают и **отказы** (403/404) — для аудита попытка важнее, чем успех. Запись
дублируется в таблицу `audit_logs` и в файл `logs/audit-*.log` с ротацией: файл
останется, даже если запись в БД не удалась.

Реализация: `src/middleware/audit.js`.

### Мера №9. Защита от массового присвоения (mass assignment)

**Почему для этого проекта.** Самая опасная уязвимость этого типа здесь —
`{"email": "...", "password": "...", "role": "admin"}` при регистрации: один
лишний ключ в JSON давал бы себе права администратора. Второй вариант —
`{"ownerId": "<чужой id>"}` при правке сравнения, то есть передача своей записи
другому пользователю или присвоение чужой.

**Три независимых рубежа:**

1. Joi-схемы объявлены строгими (`allowUnknown: false`) — неизвестное поле
   возвращает 400, а не игнорируется молча;
2. в схемах создания и правки перечислены **только** разрешённые поля
   (`title`, `fileA`, `fileB`); `role`, `ownerId`, `author`, `id`, `stats` в них отсутствуют;
3. контроллеры присваивают поля **поимённо** — `Diff.create({title, author: req.user.email, …})`,
   а не `Diff.create(req.body)`. Даже если валидатор когда-нибудь ослабят, лишнее
   поле в модель не попадёт.

Попытка прислать служебное поле фиксируется в security-логе как
`MASS_ASSIGNMENT_ATTEMPT`: это не опечатка пользователя, а целенаправленное действие.

Реализация: `src/middleware/validate.js`, `src/validation/*.schemas.js`, контроллеры.

### Мера №12. Ограничение размера тела запроса (защита от DoS)

**Почему для этого проекта.** Сервис принимает **содержимое файлов** — то есть
по природе большие тела запросов. Без лимита один запрос с телом на 500 МБ
исчерпает память процесса; к тому же алгоритм LCS имеет сложность O(n·m) по числу
строк, и файл на миллион строк займёт процессор надолго.

**Два уровня.** `express.json({ limit: '100kb' })` отвергает запрос с 413 **до**
разбора JSON, то есть память на парсинг не расходуется вовсе. Второй уровень —
Joi и валидатор модели ограничивают каждое поле `content` 100 КБ по отдельности.

Реализация: `src/app.js`, `src/validation/diff.schemas.js`.

### Мера №13. Content Security Policy через helmet

**Почему для этого проекта.** Сервис **обязан** хранить и показывать произвольный
HTML и JS — это содержимое сравниваемых файлов, вырезать его нельзя. Поэтому CSP
здесь не «ещё один заголовок», а основная страховка: даже если где-то в клиенте
появится небезопасная вставка в DOM, директива `script-src 'self'` не даст
выполнить inline-скрипт.

Политика жёсткая, с `useDefaults: false`:

```
default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:;
connect-src 'self'; font-src 'self'; object-src 'none'; base-uri 'self';
form-action 'self'; frame-ancestors 'none'
```

Ради этой политики стили и скрипты демо-страницы вынесены в отдельные файлы
(`public/styles.css`, `public/app.js`) — inline-кода на странице нет.

Реализация: `src/middleware/securityHeaders.js`.

### Мера №15. Валидация Content-Type (только `application/json`)

**Почему для этого проекта.** Это не формальность, а анти-CSRF мера. HTML-форма
умеет отправлять только три типа содержимого (`x-www-form-urlencoded`,
`multipart/form-data`, `text/plain`), и такие запросы браузер считает «простыми» —
они уходят на чужой домен **без** preflight-проверки CORS. Требование
`application/json` заставляет браузер делать preflight, который наш CORS-белый
список отклоняет. В результате классическая CSRF-атака формой
`<form action="http://api/api/diffs" method="POST">` перестаёт работать.

Реализация: `src/middleware/contentType.js`, ответ 415.

### Мера №16. Временный токен сброса пароля (1 час)

**Почему для этого проекта.** Политика сложности (мера №3) и блокировка (мера №6)
увеличивают число ситуаций «не могу войти». Без механизма сброса пользователь
теряет доступ ко всей своей истории сравнений.

**Детали.** Токен — 48 случайных байт (`crypto.randomBytes`), в БД хранится только
его SHA-256 хеш. Срок жизни 1 час, токен **одноразовый**: после использования
обнуляется. Успешный сброс поднимает `tokenVersion`, отзывает все сессии и
снимает блокировку входа.

Ответ на `/auth/forgot-password` — всегда 202 с одинаковым текстом, независимо от
того, зарегистрирован адрес или нет: иначе эндпоинт превращается в средство
проверки, кто есть в системе. Почтовый сервис в лабораторной работе не поднимался,
поэтому при `NODE_ENV=development` токен возвращается в поле `devResetToken` —
в production он только логируется.

Реализация: `src/controllers/auth.controller.js`.

### Мера №18. Заголовок `X-Frame-Options: DENY`

**Почему для этого проекта.** Защита от clickjacking: без этого заголовка
страницу сервиса можно встроить прозрачным `<iframe>` в чужой сайт и получить
клик пользователя по кнопке «Удалить». Ставится и современный аналог —
`frame-ancestors 'none'` в CSP, и устаревший `X-Frame-Options` для старых браузеров.

Реализация: `src/middleware/securityHeaders.js`, `frameguard: { action: 'deny' }`.

### Мера №19. Санитизация входных данных (удаление HTML-тегов)

**Главное решение этой меры — что НЕ санитизировать.**

| Поле | Санитизация | Почему |
|---|:--:|---|
| `title`, `fileA.name`, `fileB.name`, `email` | ✅ теги вырезаются | это метаданные, HTML в них не нужен |
| `fileA.content`, `fileB.content` | ❌ **не трогаем** | это содержимое сравниваемых файлов. Вырезать теги из HTML-файла — значит сломать саму функцию сервиса |
| `password` и производные | ❌ не трогаем | пароль должен попасть в bcrypt ровно таким, каким его ввели |

Безопасность неочищенных полей обеспечивается **экранированием на выводе**:
клиент вставляет текст только через `textContent`, `innerHTML` не используется
нигде. Это правильный порядок — санитизация на входе уничтожает данные,
экранирование на выводе их сохраняет.

**Нюанс реализации.** `sanitize-html` не только вырезает теги, но и экранирует
безопасные символы: заголовок `migration.sql: v1 -> v2` превратился бы в
`v1 -&gt; v2` и в таком виде лёг бы в базу. Поскольку в БД хранится чистый текст,
а экранированием занимается вывод, сущности раскодируются обратно. Обратная
сторона: раскодированная строка `&lt;script&gt;` стала бы настоящим тегом, поэтому
цикл «вырезать теги → раскодировать сущности» повторяется до стабилизации
(2–3 итерации). Итог — в значении нет тегов ни в каком виде кодирования:

| Вход | Результат |
|---|---|
| `migration.sql: v1 -> v2` | `migration.sql: v1 -> v2` |
| `<script>alert(1)</script>Отчёт` | `Отчёт` |
| `&lt;script&gt;alert(1)&lt;/script&gt;Отчёт` | `Отчёт` |
| `&amp;lt;script&amp;gt;alert(1)&amp;lt;/script&amp;gt;` | *(пусто)* |
| `<img src=x onerror=alert(1)>файл` | `файл` |

Попутно вырезаются ключи `__proto__`, `constructor`, `prototype` (защита от
prototype pollution) и ограничивается глубина обхода объекта.

Реализация: `src/middleware/sanitize.js`.

### Мера №20. Ограничение числа одновременных сессий

**Почему для этого проекта.** Утечка refresh-токена иначе остаётся незамеченной:
атакующий работает параллельно с владельцем сколько угодно долго. Лимит в 3
активные сессии делает утечку заметной — у владельца «неожиданно» пропадает вход
на одном из устройств. Плюс `GET /auth/sessions` показывает IP и User-Agent всех
сессий, а `POST /auth/logout-all` закрывает их одной командой.

При превышении лимита самая старая сессия отзывается, а событие
`SESSION_LIMIT_EXCEEDED` пишется в security-лог.

Реализация: `src/services/token.service.js`, функция `enforceSessionLimit`.

### Мера №22. CORS с белым списком доменов

**Почему для этого проекта.** В предыдущей версии стояло
`Access-Control-Allow-Origin: *` — любой сайт мог вызывать API из браузера
пользователя. С появлением cookie это ещё и технически невозможно: по
спецификации CORS нельзя одновременно использовать `*` и `credentials: true`,
а refresh-токен у нас живёт именно в cookie.

Список разрешённых origin берётся из `CORS_WHITELIST` в `.env`. Запросы **без**
заголовка `Origin` (Postman, curl, серверные интеграции) пропускаются осознанно:
CORS — ограничение браузера, а не механизм аутентификации, блокировать им
консольные клиенты бессмысленно; доступ всё равно решает JWT.

Проверено: для `Origin: http://localhost:3000` возвращается
`Access-Control-Allow-Origin: http://localhost:3000`, для
`Origin: http://evil.example.com` заголовков `Access-Control-Allow-*` нет вовсе,
и браузер блокирует чтение ответа. Событие — `CORS_ORIGIN_REJECTED`.

Реализация: `src/middleware/corsWhitelist.js`.

### Мера №24. Generic errors в production

**Почему для этого проекта.** Сообщение вида `relation "diffs" does not exist`
или `ECONNREFUSED 127.0.0.1:5432` раскрывает СУБД, схему и топологию — готовая
разведка для атакующего (OWASP A05, Security Misconfiguration). Стек вызовов
вдобавок выдаёт пути файлов и версии библиотек.

**Логика обработчика.** Ошибки делятся на операционные и неожидаемые:

- операционные (`ApiError`: 400/401/403/404/409/413/415/423/429) отдаются с их
  текстом в любом окружении — пользователю нужно знать, что он прислал не так;
- любая неожидаемая ошибка в production превращается в
  `{"error": "Внутренняя ошибка сервера", "requestId": "..."}`. Полные
  подробности уходят только в `logs/error-*.log` под тем же `requestId`,
  по которому администратор найдёт запись;
- в development к ответу добавляются `devMessage` и `devStack` — иначе отлаживать
  невозможно.

Отдельно нормализуются ошибки Sequelize: `UniqueConstraintError` → 409
«email уже зарегистрирован», `ValidationError` → 400 со списком сообщений,
а `DatabaseError` → 500 generic, потому что его текст может содержать SQL.

Реализация: `src/middleware/errorHandler.js`.

### Мера №25. Rate limiting отдельно по user ID

**Почему для этого проекта.** Лимит по IP работает плохо в обе стороны: за одним
NAT университетской сети сидят десятки людей, и общий лимит наказывает всех из-за
одного; а один аккаунт, работающий из множества адресов, IP-лимит обходит. Ключ
по `user.id` решает оба случая.

Реализовано два лимитера с ключом по пользователю: `userLimiter` (60 запросов /
15 мин на защищённые маршруты) и более строгий `writeLimiter` (30 запросов /
15 мин на POST/PUT/PATCH/DELETE) — запись дороже чтения, потому что POST
запускает вычисление diff. Для анонимных запросов ключ падает обратно на IP,
причём через `ipKeyGenerator`, который нормализует IPv6 до /64-подсети: иначе
лимит обходится сменой последних групп адреса.

Реализация: `src/middleware/rateLimiters.js`.

### Мера №29. Валидация query-параметров на SQL-инъекции

**Честная формулировка.** Инъекции в этом проекте технически невозможны и без
этой меры: все запросы строит Sequelize параметризованно. Детектор ниже не
«защищает», а **выявляет попытку** — чтобы она попала в security-лог как
подозрительное действие и была видна при разборе инцидента.

Работает в два шага:

1. Joi-схема строки запроса (`listQuery`) описывает каждый допустимый параметр
   типом и границами; любой другой параметр (`?id=1 OR 1=1`, `?sort=…`) даёт 400
   ещё до обращения к БД;
2. `detectInjectionInQuery` проверяет значения query и `:id` по шаблонам
   (`UNION SELECT`, `OR 1=1`, `--`, `pg_sleep(`, `$where`, `$ne` и т. п.),
   пишет `SQL_INJECTION_ATTEMPT` и отвечает 400.

**Тело запроса этим детектором не проверяется осознанно:** в diff-сервисе
пользователь имеет полное право сравнивать `.sql`-файлы, в которых встречается
`DROP TABLE`. Проверено: такой запрос возвращает 201, строка сохраняется
дословно, таблица `users` остаётся на месте.

Реализация: `src/middleware/sanitize.js`, `src/validation/diff.schemas.js`.

### Мера №30. Логирование ошибок в отдельный файл с ротацией

**Почему для этого проекта.** Мера №24 скрывает подробности от пользователя — значит,
они должны быть доступны администратору, иначе ошибки станут неотлаживаемыми.
Отдельный файл нужен, чтобы ошибки не тонули в потоке обычных запросов.

Ротация: новый файл каждый день, архивы жмутся в `.gz`, хранятся 14 дней, размер
одного файла ограничен 5 МБ. Без ротации лог-файл — сам по себе вектор DoS:
атакующий генерирует ошибки, пока не кончится диск.

Реализация: `src/utils/logger.js`, транспорт `DailyRotateFile`.

### 7.1. Аутентификация — `src/middleware/authenticate.js`

```js
function authenticate(options = {}) {
  const { optional = false } = options;

  return async (req, res, next) => {
    const token = extractToken(req);          // Authorization: Bearer <token>

    if (!token) {
      if (optional) return next();            // публичный GET продолжается анонимно
      logSuspicious('AUTH_MISSING_TOKEN', req);
      return next(ApiError.unauthorized('Не передан токен доступа'));
    }

    let payload;
    try {
      payload = verifyAccessToken(token);
    } catch (error) {
      if (error instanceof jwt.TokenExpiredError) {
        logSuspicious('AUTH_TOKEN_EXPIRED', req);
        return next(ApiError.unauthorized('Срок действия токена истёк'));
      }
      // Неверная подпись — почти всегда попытка подделать токен
      logSuspicious('AUTH_TOKEN_INVALID', req, { reason: error.message });
      return next(ApiError.unauthorized('Недействительный токен доступа'));
    }

    const user = await User.findByPk(payload.sub);

    if (!user)            return next(ApiError.unauthorized('Пользователь токена не найден'));
    if (user.isLocked())  return next(ApiError.locked('Аккаунт временно заблокирован'));
    if (payload.tv !== user.tokenVersion) {
      logSuspicious('AUTH_TOKEN_REVOKED', req, { userId: user.id });
      return next(ApiError.unauthorized('Токен отозван, войдите заново'));
    }

    req.user = user;   // роль берём из БД, а НЕ из payload
    return next();
  };
}
```

Ключевое решение: роль читается **из базы**, а не из payload токена. Иначе
понижение роли администратором не подействовало бы до истечения access-токена.
Проверка `tokenVersion` даёт возможность мгновенно обесценить все выданные токены.

### 7.2. Ролевая модель — `src/middleware/roleGuard.js`

```js
const ROLE_LEVEL = { user: 1, moderator: 2, admin: 3 };

function roleGuard(requiredRole) {
  if (!ROLE_LEVEL[requiredRole]) {
    throw new Error(`roleGuard: неизвестная роль "${requiredRole}"`);
  }

  return (req, res, next) => {
    if (!req.user) return next(ApiError.unauthorized('Требуется аутентификация'));

    const actual = ROLE_LEVEL[req.user.role] || 0;
    if (actual < ROLE_LEVEL[requiredRole]) {
      logSuspicious('FORBIDDEN_ROLE', req, {
        requiredRole, actualRole: req.user.role,
      });
      return next(ApiError.forbidden(
        `Операция доступна только для роли "${requiredRole}" и выше`));
    }
    return next();
  };
}

/** Свой ресурс — можно; чужой — только модератору и админу. */
function ownerOrRole(loader, ownerField = 'ownerId', overrideRole = 'moderator') {
  return async (req, res, next) => {
    const resource = await loader(req);
    if (!resource) return next(ApiError.notFound('Ресурс не найден'));

    req.resource = resource;

    const isOwner = resource[ownerField] && resource[ownerField] === req.user.id;
    const canOverride = (ROLE_LEVEL[req.user.role] || 0) >= ROLE_LEVEL[overrideRole];

    if (!isOwner && !canOverride) {
      logSuspicious('FOREIGN_RESOURCE_ACCESS', req, {
        resourceId: resource.id, resourceOwner: resource[ownerField],
      });
      return next(ApiError.forbidden('Можно изменять только свои записи'));
    }
    return next();
  };
}
```

Роли проверяются по **уровню**, а не по равенству: `admin` автоматически проходит
там, где достаточно `moderator`. Опечатка в названии роли роняет приложение при
старте, а не тихо открывает маршрут.

### 7.3. Валидация — `src/middleware/validate.js`

```js
const OPTIONS = {
  abortEarly: false,     // вернуть сразу все ошибки, а не первую
  allowUnknown: false,   // неизвестное поле = 400 -> защита от mass assignment
  stripUnknown: false,   // не вырезаем молча, а явно сообщаем
  convert: true,         // "limit=5" из query -> число 5
  messages: MESSAGES,    // локализация системных сообщений Joi
};

function validate(schema, source = 'body') {
  return (req, res, next) => {
    const { value, error } = schema.validate(req[source], OPTIONS);

    if (error) {
      const details = error.details.map((d) => d.message);

      // Попытка подсунуть служебное поле — признак целенаправленной атаки
      const forbidden = error.details
        .filter((d) => d.type === 'object.unknown')
        .map((d) => d.path.join('.'));
      if (forbidden.length > 0) {
        logSuspicious('MASS_ASSIGNMENT_ATTEMPT', req, { source, fields: forbidden });
      }

      return next(ApiError.badRequest('Некорректные данные запроса', details));
    }

    req[source] = value;   // дальше в контроллер идут только проверенные данные
    return next();
  };
}
```

```js
function errorHandler(err, req, res, next) {
  const error = normalize(err);        // ошибки Sequelize -> ApiError
  const status = error.status || 500;
  const requestId = crypto.randomUUID();

  // Полная информация — ТОЛЬКО в лог-файл (logs/error-*.log, мера №30)
  if (status >= 500) {
    const payload = {
      requestId, method: req.method, url: req.originalUrl, ip: clientIp(req),
      userId: req.user?.id, originalMessage: err.message, stack: err.stack, sql: err.sql,
    };
    logger.error(`Необработанная ошибка: ${err.message}`, payload);
    errorLogger.error(`Необработанная ошибка: ${err.message}`, payload);
  }

  const body = { error: error.message };
  if (error.details) body.details = error.details;

  if (status >= 500) {
    body.error = 'Внутренняя ошибка сервера';   // generic error (мера №24)
    body.requestId = requestId;
    if (!config.isProduction) {                 // подробности — только в разработке
      body.devMessage = err.message;
      body.devStack = (err.stack || '').split('\n').slice(0, 6);
    }
  }

  res.status(status).json(body);
}
```

## 12. Ответы на контрольные вопросы

### 1. Какие роли вы реализовали и каковы их права доступа? Как это связано с вашим курсовым проектом?

Реализованы три роли с нарастающими полномочиями:

- **`user`** — зарегистрированный пользователь: создаёт сравнения, редактирует
  только свои записи, читает публичные;
- **`moderator`** — всё, что `user`, плюс правка **чужих** сравнений и просмотр
  списка пользователей;
- **`admin`** — всё, что `moderator`, плюс удаление сравнений и пользователей,
  смена ролей, снятие блокировок, просмотр audit log.

`roleGuard(role)` сравнивает **уровни** (`user`=1, `moderator`=2, `admin`=3), а не
названия, поэтому `admin` автоматически проходит там, где достаточно `moderator`.

Связь с проектом: сервис хранит чужой исходный код, поэтому уровень «просто
залогинен» недостаточен — нужна ещё и проверка владения ресурсом. Роль
`moderator` появилась из реальной потребности: кто-то должен чистить мусорные
и ошибочные сравнения, не получая при этом права удалять пользователей.
Разделение «модератор правит контент — администратор управляет людьми»
соответствует принципу наименьших привилегий.

### 2. Как вы храните пароли? Как обеспечивается защита от перебора (brute force)?

Пароль в открытом виде не хранится и не логируется никогда. В колонке
`users.passwordHash` лежит bcrypt-хеш с **12 раундами** соли. bcrypt сам
генерирует уникальную соль на каждый пароль (поэтому одинаковые пароли дают
разные хеши, и радужные таблицы бесполезны) и намеренно «растягивает»
вычисление — около 0,3 с на хеш, что делает перебор по украденной базе
экономически бессмысленным.

Защита от перебора — **три независимых рубежа**:

1. **Rate limiting по IP** — 10 запросов к `/auth/*` за 15 минут
   (`authLimiter`). Работает до обращения к БД, отсекает флуд.
2. **Блокировка аккаунта** (мера №6) — 5 неудачных попыток → `lockUntil = now + 15 мин`.
   Ключ — пользователь, а не IP, поэтому распределённый перебор с пула адресов
   тоже не проходит. При блокировке отзываются все активные сессии.
3. **Политика сложности** (мера №3) — пароль из словаря или короткий просто
   не заводится.

Дополнительно: ответ 401 одинаков для «нет такого email» и «неверный пароль»,
а `burnTime()` выравнивает время ответа, поэтому аккаунты нельзя перечислить ни
по тексту, ни по скорости.

### 3. Как вы защитили API от SQL-инъекций (или NoSQL-инъекций)?

Основная и достаточная защита — **ORM Sequelize**. Все без исключения обращения
к базе идут через методы модели (`findAll`, `findByPk`, `create`, `update`,
`destroy`); сырого SQL (`sequelize.query`) в проекте нет. Sequelize формирует
параметризованные запросы: текст запроса и значения уходят в драйвер `pg`
раздельно:

```sql
INSERT INTO "diffs" ("id","title","author", ...) VALUES ($1,$2,$3, ...)
```

Поэтому строка `' OR 1=1 --` попадает в БД как обычный текст и не может изменить
структуру запроса. Операторы вроде `Op.iLike` тоже подставляют значение
параметром:

```js
where[Op.or] = [{ title: { [Op.iLike]: `%${search}%` } }, ...];
```

Дополнительные (не основные) рубежи:

- Joi описывает каждый допустимый параметр строки запроса типом и границами;
  всё постороннее отвергается с 400 **до** обращения к БД;
- детектор `detectInjectionInQuery` ищет характерные конструкции
  (`UNION SELECT`, `OR 1=1`, `--`, `pg_sleep(`) и пишет `SQL_INJECTION_ATTEMPT`
  в security-лог. Это средство **обнаружения**, а не защиты;
- в единственном месте, где идентификатор нельзя передать параметром
  (`CREATE DATABASE` в `scripts/createDatabase.js`), имя БД проверяется
  регулярным выражением и экранируется как идентификатор.

Проверено практически: сравнение двух `.sql`-файлов с текстом
`DROP TABLE users; -- ' OR 1=1 --` создалось с кодом 201, строка сохранилась
дословно, таблица `users` не пострадала.

### 4. Какую библиотеку валидации вы использовали? Приведите пример проверки email.

Использован **Joi** (версия 18) — как основной валидатор на границе API, плюс
встроенные валидаторы Sequelize как второй рубеж на уровне модели.

Проверка email в `src/validation/common.js`:

```js
const email = Joi.string()
  .trim()                 // убрать случайные пробелы
  .lowercase()            // нормализовать регистр: Ivan@X.by и ivan@x.by — один адрес
  .max(254)               // ограничение длины адреса по RFC 5321
  .email({ minDomainSegments: 2, tlds: { allow: false } })
  .messages({
    'string.email': 'Некорректный формат email',
    'string.max': 'Email не должен превышать 254 символов',
    'any.required': 'Поле "email" обязательно',
  });
```

`minDomainSegments: 2` требует домен вида `name@example.com` (адрес `a@localhost`
не пройдёт). `tlds: { allow: false }` отключает сверку домена верхнего уровня со
списком IANA — иначе не работали бы учебные адреса вида `admin@diffservice.local`.

Тот же email проверяется ещё раз на уровне модели:

```js
email: {
  type: DataTypes.STRING(254), allowNull: false, unique: true,
  validate: { isEmail: { msg: 'Некорректный формат email' } },
}
```

Это страховка на случай, если запись создадут в обход слоя маршрутов (например,
из сидера или миграции).

### 5. Какие меры защиты от XSS вы приняли (helmet, экранирование)?

Четыре уровня, выстроенные по принципу «экранировать на выводе, а не уничтожать
на входе»:

1. **Экранирование на выводе — основная мера.** Клиент строит DOM только через
   `document.createElement` и `textContent`; `innerHTML` не используется нигде в
   `public/app.js`. Поэтому `<img src=x onerror=alert(1)>` в содержимом файла
   отображается как текст и никогда не становится узлом DOM.
2. **CSP через helmet** (мера №13): `script-src 'self'`, `style-src 'self'`,
   `object-src 'none'`, `base-uri 'self'`. Inline-скрипты запрещены — даже если в
   страницу каким-то образом попадёт `<script>`, браузер его не выполнит.
   Ради этого стили и скрипты вынесены в отдельные файлы.
3. **Санитизация на входе** (мера №19): из **метаданных** (`title`, имена файлов)
   HTML-теги вырезаются `sanitize-html`. Из **содержимого файлов** — нет,
   это данные сервиса.
4. **Сопутствующие заголовки:** `X-Content-Type-Options: nosniff` (ответ
   `text/plain` не будет исполнен как HTML), `X-Frame-Options: DENY` и
   `frame-ancestors 'none'` против clickjacking.

### 6. Как вы настроили глобальное ограничение частоты запросов (rate limiting)?

Библиотека `express-rate-limit`, четыре независимых лимитера:

| Лимитер | Ключ | Лимит | Где применяется |
|---|---|---|---|
| `globalLimiter` | IP | 300 / 15 мин | всё приложение (`app.use`) |
| `authLimiter` | IP | 10 / 15 мин | `/auth/login`, `/register`, `/refresh`, `/forgot-password` |
| `userLimiter` | user ID | 60 / 15 мин | защищённые маршруты |
| `writeLimiter` | user ID | 30 / 15 мин | POST / PUT / PATCH / DELETE |

Глобальный лимитер подключён в `src/app.js` **до** разбора тела, чтобы флуд
отсекался до траты памяти на парсинг:

```js
const globalLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: config.security.rateLimitMax,
  standardHeaders: 'draft-7',    // заголовки RateLimit-Limit / -Remaining / -Reset
  legacyHeaders: false,
  handler: makeHandler('RATE_LIMIT_GLOBAL'),   // лог + единообразный JSON с 429
});
app.use(globalLimiter);
```

Все значения настраиваются через `.env`. Для корректного определения IP за
прокси выставлено `app.set('trust proxy', 1)`, а для IPv6 используется
`ipKeyGenerator`, нормализующий адрес до /64-подсети — иначе лимит обходится
сменой последних групп адреса. Каждое срабатывание пишется в security-лог.

### 7. Что такое JWT? Как вы обеспечиваете его безопасное хранение и передачу?

**JWT (JSON Web Token)** — компактный самодостаточный токен из трёх частей,
разделённых точками: заголовок (алгоритм и тип), payload (полезная нагрузка) и
подпись. Части закодированы Base64URL — это **кодирование, а не шифрование**:
payload читается кем угодно. Подпись (у нас HMAC-SHA256 на секрете из `.env`)
позволяет серверу убедиться, что токен не подменён, не обращаясь к БД за сессией.

**Что кладём в payload:** только `sub` (id пользователя), `role`, `tv`
(версия токенов), `type` и служебные `exp`/`iss`. Никаких персональных данных —
payload не зашифрован.

**Хранение и передача:**

| | access-токен | refresh-токен |
|---|---|---|
| Срок жизни | 15 минут | 7 дней |
| Секрет | `JWT_SECRET` | **другой**: `JWT_REFRESH_SECRET` |
| Передача | заголовок `Authorization: Bearer` | `HttpOnly; SameSite=Strict` cookie |
| Хранение на клиенте | переменная в памяти JS | недоступен JS вообще |
| Хранение на сервере | не хранится | SHA-256 хеш в таблице `sessions` |

Ключевые решения:

- access-токен **не** кладётся в `localStorage`: оттуда его прочитает любой
  скрипт на странице. Переменная в памяти исчезает при закрытии вкладки;
- refresh-токен в `HttpOnly` cookie недоступен JavaScript, поэтому XSS не уводит
  долгоживущий токен; `SameSite=Strict` закрывает CSRF; `Secure` включается в
  production (только по HTTPS);
- алгоритм зафиксирован списком `algorithms: ['HS256']` при проверке — иначе
  возможна классическая атака подменой заголовка на `alg: none`;
- роль читается из БД, а не из payload, поэтому её понижение действует сразу;
- `tokenVersion` позволяет мгновенно обесценить все выданные токены
  (смена пароля, смена роли, `logout-all`).

### 9. Как вы логируете подозрительные действия? Приведите пример записи в логе.

```js
function logSuspicious(event, req, details = {}) {

    userAgent: req?.get ? req.get('user-agent') : undefined,
    userId: req?.user?.id,
    userEmail: req?.user?.email,

  });
}
```

Пример реальной записи — блокировка после перебора пароля:

### 10. Как вы организовали защиту от CSRF?

Отдельная библиотека (`csurf`) не подключалась — её роль здесь выполняют три
механизма, работающие вместе:

1. **Основной способ аутентификации — заголовок, а не cookie.** Access-токен
   передаётся в `Authorization: Bearer`, а заголовок браузер автоматически к
   кросс-доменному запросу не добавляет. CSRF опасна именно тем, что cookie
   прикрепляется сама, а здесь на cookie держится только `/auth/refresh`.
2. **`SameSite=Strict` на refresh-cookie.** Браузер не отправит её при запросе,
   инициированном с чужого сайта, поэтому форма или `fetch` со стороннего домена
   не сможет обновить токен.
3. **Требование `Content-Type: application/json`** (мера №15). HTML-форма умеет
   отправлять только `x-www-form-urlencoded`, `multipart/form-data` и
   `text/plain`; такие запросы уходят без preflight. Требуя JSON, мы заставляем
   браузер делать preflight, а его отклоняет CORS-белый список (мера №22).

Итог: классическая атака `<form action="http://api/api/diffs" method="POST">`
не проходит — она получит 415, а `fetch` с чужого origin не пройдёт preflight.

### 11. Как вы реализовали refresh-токены или ограничение количества сессий?

**Refresh-токены (мера №5).** При входе выдаётся пара: access (15 минут,
заголовок) и refresh (7 дней, `HttpOnly; SameSite=Strict` cookie), подписанные
**разными** секретами. В таблице `sessions` хранится не сам токен, а его
SHA-256 хеш — утечка базы не даёт возможности войти.

**Ротация.** Каждый вызов `/auth/refresh` отзывает старую сессию и создаёт новую:

```js
await tokens.revokeSession(session);
const pair = await tokens.issueTokenPair(user, req);
setRefreshCookie(res, pair);
```

Если приходит refresh-токен с верной подписью, но **без** активной сессии —
значит, токен уже был использован. Это признак кражи: система отзывает все
сессии пользователя и пишет `REFRESH_TOKEN_REUSE`.

**Ограничение сессий (мера №20).** Перед выдачей новой пары проверяется число
активных сессий; при превышении `MAX_SESSIONS_PER_USER` (по умолчанию 3) самые
старые отзываются:

```js
async function enforceSessionLimit(userId, req) {
  const active = await Session.findAll({
    where: { userId, revokedAt: null, expiresAt: { [Op.gt]: new Date() } },
    order: [['createdAt', 'ASC']],
  });
  if (active.length < limit) return;

  const excess = active.slice(0, active.length - limit + 1);
  await Promise.all(excess.map((s) => s.update({ revokedAt: new Date() })));
  logSuspicious('SESSION_LIMIT_EXCEEDED', req, { userId, limit });
}
```

Пользователь видит свои сессии (IP, User-Agent, время) через `GET /auth/sessions`
и может закрыть все сразу: `POST /auth/logout-all`, который дополнительно
поднимает `tokenVersion` и обесценивает выданные access-токены.

### 12. Как вы обрабатываете ошибки, чтобы не раскрывать детали реализации (generic errors)?

Все ошибки проходят через единственный обработчик `src/middleware/errorHandler.js`,
который делит их на **операционные** и **неожидаемые**:

- операционные (`ApiError`: 400, 401, 403, 404, 409, 413, 415, 423, 429) отдаются
  с их текстом в любом окружении — пользователь должен понимать, что он прислал
  не так;
- любая неожидаемая ошибка (баг, недоступная БД, сбой драйвера) в production
  превращается в `{"error": "Внутренняя ошибка сервера", "requestId": "..."}`;
- в development к ответу добавляются `devMessage` и `devStack` (6 строк) — иначе
  отлаживать невозможно.

Отдельно нормализуются ошибки Sequelize: `UniqueConstraintError` → 409
«email уже зарегистрирован», `ValidationError` → 400 со списком сообщений,
а **`DatabaseError` → 500 generic**, потому что его текст может содержать
фрагмент SQL и имена таблиц.

Полная информация (стек, `err.sql`, исходное сообщение, IP, userId) пишется в
`logs/error-*.log` под тем же `requestId`, который получил пользователь, — по
нему администратор находит запись. Проверено: при недоступной БД клиент получает
только `{"error":"Внутренняя ошибка сервера","requestId":"783cfdae-..."}`.

Сопутствующие решения той же цели: `X-Powered-By` удалён; 404 не перечисляет
доступные маршруты; `toJSON()` модели `User` вырезает `passwordHash` даже при
случайном `res.json(user)`.

### 13. Как вы ограничиваете размер тела запроса для защиты от DoS?

Два уровня.

**Уровень 1 — до разбора JSON.** Лимит задаётся при подключении парсера:

```js
app.use(express.json({ limit: config.security.bodyLimit, strict: true }));  // 100kb
```

Тело сверх лимита отвергается с 413 **до** парсинга, то есть память на разбор не
расходуется вовсе. Ошибку `entity.too.large` обработчик превращает в понятный
ответ с указанием лимита.

**Уровень 2 — по полям.** Joi и валидатор модели ограничивают каждое поле
`content` ста килобайтами по отдельности, а `title` — 120 символами.

Это особенно важно именно для diff-сервиса: алгоритм LCS имеет сложность O(n·m)
по числу строк, поэтому без ограничения один запрос с файлом на миллион строк
занял бы процессор надолго. Лимит настраивается переменной `BODY_LIMIT`.

### 14. Как вы проверяете сложность пароля? Приведите требования.

Функция `checkPasswordStrength` в `src/utils/password.js`, подключённая к Joi
через `.custom()`. Требования:

| Требование | Проверка |
|---|---|
| минимум 8 символов | `password.length < 8` |
| максимум 128 символов | bcrypt учитывает первые 72 байта; длинные режем заранее |
| строчная латинская буква | `/[a-z]/` |
| заглавная латинская буква | `/[A-Z]/` |
| цифра | `/[0-9]/` |
| специальный символ | `/[^A-Za-z0-9]/` |
| без пробелов | `/\s/` |
| не из списка 20 самых распространённых | `BLACKLIST.has(password.toLowerCase())` |

Функция возвращает **список всех** нарушенных правил сразу, а не первое:
иначе пользователь угадывал бы требования методом перебора. Пример ответа:

```json
{
  "error": "Некорректные данные запроса",
  "details": [
    "Пароль не соответствует политике (Пароль должен содержать заглавную латинскую букву; Пароль должен содержать специальный символ). Требования: минимум 8 символов, заглавная и строчная латинские буквы, цифра и спецсимвол, без пробелов"
  ]
}
```

Важная деталь: при **входе** пароль на сложность не проверяется — иначе по тексту
ошибки можно было бы отличить «пароль слабый» от «пароль неверный».

## 14. Выводы

В ходе работы REST API сервиса сравнения файлов был доведён от простого CRUD с
хранением в памяти до приложения с полноценной системой безопасности.

**Что сделано:**

- хранилище переведено на PostgreSQL через ORM Sequelize — все запросы
  параметризованы, что закрывает SQL-инъекции на архитектурном уровне;
- реализована аутентификация на JWT с разделением access- и refresh-токенов,
  ротацией refresh и обнаружением его повторного использования;
- внедрена ролевая модель из трёх ролей с проверкой не только роли, но и
  владения конкретным ресурсом;
- валидация покрывает **все** эндпоинты, принимающие данные: тело, параметры
  пути и строку запроса;
- реализованы 8 обязательных и 13 дополнительных мер безопасности из таблицы
  задания при требуемом минимуме в три;
- настроено логирование 21 типа подозрительных событий в отдельный файл с
  ротацией плюс audit log действий администратора;
- подготовлены документация API, коллекция Postman на 61 запрос и скрипт
  автоматического тестирования на 49 проверок (49/49 пройдено).

**Основные выводы:**

1. **Безопасность — это слои, а не одна «правильная» библиотека.** Защиту от
   перебора пароля дают три независимых механизма (rate limit по IP, блокировка
   аккаунта, политика сложности), и каждый закрывает то, что пропускают
   остальные: IP-лимит бессилен против распределённой атаки, блокировка
   аккаунта — против флуда по разным аккаунтам, а политика сложности — против
   единственной удачной попытки.

2. **Порядок middleware — часть защиты.** Выстраивание цепочки от дешёвых
   проверок к дорогим (origin → лимит → Content-Type → разбор тела → БД →
   bcrypt) означает, что атака упирается в ограничение раньше, чем успевает
   нагрузить систему.

3. **Самое сложное решение в работе — что НЕ защищать.** Санитизация содержимого
   сравниваемых файлов сломала бы саму функцию сервиса. Правильный ответ —
   хранить данные как есть и экранировать их на выводе, а CSP держать как
   страховку. То же касается SQL-конструкций в теле запроса: для diff-сервиса
   `DROP TABLE` в `.sql`-файле — обычные данные, а не атака.

4. **Безопасность и удобство конфликтуют, и конфликт нужно разрешать явно.**
   Блокировка на 15 минут создаёт ситуацию «не могу войти» — поэтому
   понадобились эндпоинт сброса пароля и возможность для администратора снять
   блокировку. Generic errors скрывают детали от атакующего — поэтому
   понадобился `requestId` и отдельный файл ошибок, иначе система стала бы
   неотлаживаемой.

5. **Инструменты не заменяют понимания.** В ходе работы обнаружились две
   неочевидные ловушки: `dotenv` молча обрезает значение после символа `#`
   (пароль администратора превращался в `Admin`), а `sanitize-html` экранирует
   безопасные символы, из-за чего заголовок `v1 -> v2` сохранялся как
   `v1 -&gt; v2`. Обе нашлись только при реальном прогоне тестов, а не при
   чтении кода.
